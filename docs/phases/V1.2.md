## Delivered behavior

- Select a due from the list to open the existing form in edit mode. Clear the selection so the same row can be opened again after returning.
- Pass only the due id through Shell navigation. DueEditPage receives it using IQueryAttributable; the view model loads the record from SQLite.
- Populate title, amount, calendar date, optional notes, and paid status. Format amount entry with an invariant decimal point and two fractional digits.
- Edit fields and toggle paid/unpaid. The payment switch is visible only in edit mode; changes persist on Save changes. New dues still default to unpaid.
- Preserve Id and CreatedAt, update UpdatedAt from the injected clock, and normalize blank notes to null. Keep paid dues in the date-sorted list.
- Cancel/back leaves the database unchanged. Repeated load requests do not overwrite an already loaded form's unsaved edits.
- Disable editing/saving while loading or writing. Show a retry action after a load failure; retain input after a save failure.
- Reject invalid ids, unknown dues, and tombstones without falling back to create mode. A due deleted after opening cannot be restored by Save.
- Preserve the successful-save guard: overlapping Save actions and navigation retries cannot submit another write.

## Data and concurrency decisions

Load/check/update share one DatabaseDispatcher operation. This prevents other App database operations from interleaving between the active-row check and update. Save re-reads the stored row and copies only editable values onto it.

SqliteDueRepository.UpdateAsync now updates only active rows with `WHERE id = @id AND deleted_at IS NULL`; it never writes CreatedAt or DeletedAt. Missing/deleted ids throw KeyNotFoundException. This also protects against deletion by another writer after the App's read. SoftDeleteAsync remains the deletion path.

The id lookup already uses the primary key; no additional index is needed. Schema version remains 1, and no new production dependency or migration was added. Multiple external editors are not supported; this slice does not introduce optimistic concurrency or conflict resolution.

- The list displayed an existing due with no startup/read error.

- The same row could be selected again, and the reopened form's field values and paid status matched their values before the canceled change.
- A second Cancel left the app on the dues list.

No Save action was used and no saved dues were changed during the agent's UI checks.
