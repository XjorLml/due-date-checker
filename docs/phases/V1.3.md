## Delivered behavior

- Show Delete due only for an existing, loaded, available due. New forms and unavailable targets have no Delete action.
- Present a native confirmation naming the stored due, with explicit Delete and Cancel actions. Unsaved changes to the title do not change the confirmation target.
- Cancel/dismissal performs no storage call and keeps the editor and its unsaved inputs.
- Confirm sets deleted_at and updated_at to one instant from the injected clock. Keep the physical row, identity, creation timestamp, amount, date, notes, and paid status.
- Do not validate or save unfinished form edits when deleting the stored due.
- After successful deletion, return to the list and reload it. Active-list queries exclude tombstones.
- Disable editing, saving, and repeated deletion while the write is pending. Keep input and allow a newly confirmed retry after a storage failure.
- If navigation fails after deletion, offer Back to dues without repeating the deletion or saving the form.
- Keep repeated deletion idempotent: an existing tombstone retains its first deletion/update timestamps; an unknown id is a no-op.

## Implementation decisions

DueEditPage owns DisplayAlertAsync and passes the explicit Boolean choice to DueEditViewModel.DeleteCommand. The page action guard prevents overlapping confirmation dialogs and other page actions. The view model guards create/unloaded/unavailable/completed/busy states and rejects a false confirmation before touching storage.

Deletion uses the existing DatabaseDispatcher and IDueRepository.SoftDeleteAsync. SQLite executes one parameterized `UPDATE ... WHERE id = @id AND deleted_at IS NULL`; the primary-key lookup is already appropriate. No schema migration, repository implementation change, runtime package, or hard-delete path was required.

The button uses the destructive foreground/surface tokens and outlined styling from [DESIGN.md](../DESIGN.md), including a 56 dp minimum height. The dialog uses native platform styling. This approved v1 slice has no Undo/restore flow, as specified in the SDD; the broader design's future Undo interaction is deferred.

## Real-phone verification

Installed the new Release APK with `adb install -r` and launched MainActivity. Created temporary zero-amount verification dues through the app and used only those records for deletion checks; existing user dues were not edited or deleted.

The successful native check verified:

- Delete is hidden on a new form.
- The editor's Delete action opens a dialog naming the verification due.
- Native Cancel keeps the editor open and the saved due visible in the list.
- Reopening that due and confirming Delete returns to the list with the due hidden.
- After force-stopping and launching the app again, the verification due remains hidden.

The app was left on the dues list. Temporary verification records remain as hidden tombstones by design. Native checks establish UI behavior and restart visibility; retention of row fields/timestamps was verified in automated SQLite tests, not by inspecting the phone's private database.

Generated APK: `src/DueDateChecker.App/bin/Release/net10.0-android/com.lem.duedatechecker-Signed.apk`. Intended-key signing remains pending; local.signing.props was absent at the last inspection.
